This combined report presents the digital transformation strategy for SliceMatic, a single-outlet pizza delivery brand in New Ashok Nagar, Delhi. Part A — Product Requirements Document

A.1 Product Vision

SliceMatic's ordering system is a digital intake-to-bill platform that replaces phone ordering for a single-outlet pizza delivery brand in New Ashok Nagar, Delhi. It lets a customer self-serve the entire ordering journey — identity, quantity, menu selection, discount, GST, and payment — in a guided flow that computes every rupee deterministically and persists each completed order as structured, analysable data. It serves two users: the customer, who gets a fast, error-free order with a transparent bill, and the owner, who gets a queryable order database that surfaces best-sellers, peak hours, and repeat-customer behaviour. The system removes three failures of phone ordering: the single-line throughput ceiling at peak, manual pricing/GST errors, and the total absence of order data. By Stage 3 the system adds a personalised recommendation engine and an admin analytics dashboard.

What we are NOT building (at any stage):

Real payment gateway integration (confirmation only), delivery address capture/zone validation, inventory management, or mixed-pizza orders (only 1 combo type per order).

A.3 User Stories

Customer-Facing
  • As a customer, I want to place a pizza order digitally so I don't get busy signals at peak hours.
  • As a returning customer, I want a personalised recommendation based on past orders to decide faster.
  • As a new customer, I want to bypass recommendations silently and go straight to the menu.
  • As a customer, I want an itemised bill with discount and GST details so I know exactly what I pay.
  • As a customer, I want specific validation error messages so I can correct inputs without resetting.
Admin & Operator
  • As the owner, I want a secure login so only I can access sensitive business metrics.
  • As the owner, I want to filter orders by date range and payment mode to reconcile cash vs UPI.
  • As the owner, I want to see revenue, top-selling pizza, and busiest hour to optimize staffing.
  • As the owner, I want to export orders to CSV to easily share with my accountant.
  • As the operator, I want menu prices stored in a database (Stage 3) so we update them code-free.

A.5 AI Feature Specification — Recommendation Engine (Option A)

Trigger: Triggered immediately after the phone number is validated, before menu selection is shown to the customer.

Verbatim System Prompt: 
"You are a recommendation engine for SliceMatic, a pizza delivery outlet in Delhi. Based on the customer's past orders listed below, recommend ONE pizza and ONE topping they haven't tried recently — or their clear favourite if they consistently reorder it. Be brief and friendly, one or two sentences max. Respond only as JSON: {pizza: string, topping: string, reason: string}. Past orders: [order_history]"

Model Selection: Mistral 7B Instruct via OpenRouter. Latency must be capped at 5s. If it exceeds 5s, the system must trigger FR-19 (fallback): "We couldn't generate a suggestion — here's the full menu." and bypass within 3 seconds.

A.9 Edge Cases — Five-Category Framework

Empty State (No prior data / fresh states)
  • New customer: Has zero orders in Supabase. System skips the recommendation step silently and displays the menu (FR-18).
  • Admin dashboard on launch: DB contains zero orders. Admin dashboard renders a clean "No orders yet" placeholder rather than crashing or rendering blank charts.
  • Empty menu file at boot: A menu file contains 0 valid rows after parsing. System refuses to start and logs which specific file is empty.
Error State (API failures & write blocks)
  • OpenRouter HTTP errors / Timeout (>5s): Displays a friendly fallback card within 3 seconds, logging the trace, and transitions the flow straight to manual menu selection.
  • Supabase write failure: If writing the order fails at checkout, the UI displays: "Order confirmed but could not be saved. Contact operator." to keep customer reassurance without crashing.
  • File write failure (Gradio logs): If orders_log.txt is read-only, confirm the order to the customer, prompt operator warning, and preserve app state.
Boundary Conditions (Item limits & thresholds)
  • Quantity = 1 vs Quantity = 10: Both quantities are accepted. Quantity 10 does not trigger the discount threshold (FR-9 requires Qty >= 5). Quantity 11 is rejected.
  • Quantity = 5 exactly: Triggers the 10% discount logic. Subtotal line item details the exact post-discount calculation.
  • Menu Selection indexes: Entering selection 1 or N (last item) succeeds. Selection 0 or N+1 fails.
Concurrent Action & Multi-session Collision
  • Two concurrent Gradio sessions writing to logs: Known constraint in Stage 2. Replaced in Stage 3 by moving to transactional writes in Supabase.
  • Admin reads metrics while customer orders: Supabase handles concurrent database read/write isolation; admin panel does not block orders.
Permission Violations
  • Non-admin attempts to view metrics: App intercepts and redirects to Supabase Auth login. No order records are exposed in the DOM.
  • Admin tries to modify orders: Admin view is strictly read-only. No edit/delete API calls exist in the admin codebase.

A.10 Out of Scope

  • Real payment gateway processing (only mock buttons).
  • Delivery address capture or geographical distance APIs.
  • Inventory management (unlimited menu item quantities).
  • Mixed item combinations (single pizza type + topping per order block).
  • Multi-tenant logins for customers (phone number acts as session key).

A.12 Drawbacks Analysis

  • Single session state: Gradio MVP does not support isolation of state across separate tabs. Collisions occur easily during simultaneous tests.
  • Flat file log constraints: orders_log.txt will experience performance issues at scale. No indexing, slow analytics lookups.
  • Discount leaks: Hardcoded 10% discount on qty >= 5 might be exploited if average basket is high, leading to margin leaks.

Key Takeaways: Part A MoSCoW Prioritization Matrix

This prioritization framework categorises the product requirements of Part A to guide phase-by-phase implementation. It ensures developers focus on core ordering stability before building secondary database synchronisation and AI recommendation models.

MUST HAVE (Core Ordering Engine)

  • FR-1 & FR-2 Validation: Strict regex check of name (2-40 characters, letters only) and Indian phone number validation (10 digits starting with 6-9) to secure billing accuracy.
  • FR-5 Menu Loading: Local file ingestion of pizzas, bases, and toppings at boot before any customer interaction.
  • FR-7 & FR-8 Pricing: Accept number-only selections of 1 Base + 1 Pizza + 1 Topping, evaluating line totals via deterministic formula.
  • FR-10 GST & FR-11 Bill: Apply 18% GST ex-menu price post-discount, outputting aligned itemised invoice.
  • FR-13 Persistence: Local file logging of orders using pipe-separated formatting for historical records.

SHOULD HAVE (Production & Management)

  • FR-14 Supabase Integration: Transition menu loading (FR-15) and order writes (FR-16) from flat-files to multi-table transactional relational database tables (menu_items, orders, order_line_items).
  • FR-20 Admin Authentication: Protect the analytics view behind secure Supabase Auth admin logins.
  • FR-21 & FR-22 Admin Metrics: Build order table with date-range filters, payment filters, and key dashboard cards (revenue, top pizza, busiest hour).
  • FR-23 CSV Exporter: One-click export of currently filtered orders to spreadsheet files for Rajan's accountants.
  • FR-9 Discount Logic: Automated 10% discount for orders containing 5 or more pizzas, itemised on bills.

COULD HAVE (AI Personalisation)

  • FR-17 Returning Recommendations: Query database for returning phone numbers, sending last 10 orders to OpenRouter model (Mistral 7B) to recommend a pizza/topping combo before ordering.
  • FR-18 Silent Bypass: New customers with zero database records skip recommendations automatically without latency.
  • FR-19 Failure Fallback: 5-second API query limit. If the LLM call times out or throws errors, display generic warning card and load menu within 3s.

WON'T HAVE (Deferred / Out-of-Scope)

  • Real Payments Integration: UPI, card tokenisation, or payment gateways are deferred. UI supports cash, card, and UPI selections as confirmation modes only.
  • Delivery & Inventory: Capturing customer location addresses, checking stock limits, or decrementing ingredient stock lists are deferred to future stages.
  • Mixed Basket Orders: Ability to order different pizzas in a single cart session (currently limited to 1 combination type per order).
Part B — Business Analysis & Unit Economics

00 Executive Summary

SliceMatic is a viable single-outlet QSR with genuinely strong unit economics — but the reference model oversells it. After correcting one structural error, the business is healthy, not spectacular, and its real risks sit in demand ramp-up and aggregator commission, not in rent or COGS.

X Reference Model Claims
  • Contribution margin of 76% (Rs.644/order).
  • Break-even requires only 11 orders/day.
  • Operating margin of 58.9% at launch.
  • Rent sensitivity flagged as a headline risk.
✓ Corrected Deep-Dive Analysis
  • Contribution margin ~60% (Rs.511/order): Fixed double-counting delivery logic in multi-pizza baskets.
  • Break-even ~13 orders/day (own-channel), rising to 15/day blended.
  • Operating margin ~43% at mature 60% capacity (own-channel), ~35% blended.
  • Rent is not the constraint; demand ramp and aggregator mix are.
The One-Line Business Case for Digital Ordering:
Every order placed through the owned digital channel earns Rs.511 of contribution; the same order via Zomato/Swiggy earns only Rs.339 after a 25% commission. The digital ordering system exists to convert aggregator-acquired customers into owned, repeat customers. The Rs.172/order gap is the entire ROI story.

01 Market & Competitive Context

  • Delivery format is the QSR standard: ~60-70% of pizza orders are delivery. Dine-in is treated as immaterial for conservative modelling.
  • Aggregator duopoly floor: Zomato/Swiggy own early customer discovery. A new outlet will see 50-60% of early orders arrive via aggregators at 20-25% commissions.
  • Domino's standard: 30-minute delivery guarantees are a threshold requirement, not a product differentiator.
  • Locality Moat: Owned customer data (numbers, ordering behaviors) captures repeats, shifting them from commission-heavy aggregators.

17 Answers to Stage-1 Challenge Questions

Q1. Break-even if rent rises to Rs.70,000? At what rent is the model unviable?

Fixed costs increase to Rs.2,17,910. Break-even rises from 13 orders/day to ~14 orders/day (427/month). Rent is a low-sensitivity factor; rent is only unviable if it pushes fixed costs past the total contribution margin generated at planned capacity (Rs.7.2L/month, implying rent near Rs.5.7L/month).

Q2. 40% of orders via aggregator at 25% commission — new CM and break-even?

Aggregator order CM is Rs.339. The blended CM becomes 0.6 * 511 + 0.4 * 339 = Rs.442. The new break-even point increases to 15 orders/day (459/month).

Q3. At what volume is a 3rd rider justified?

Financially, under 1 extra order/day pays for a rider (Rs.16k wages / Rs.511 CM). Operationally, two riders saturate at 60-70 deliveries per day. A third rider is justified when daily volumes sustain >55 orders/day to protect delivery SLAs.

Q4. Impact of the qty >= 5 / 10% discount — value-driver or margin leak?

It cuts the order's contribution margin by ~14% (Rs.338.50). It is a value-driver only if it pulls average transaction sizes from 3-4 pizzas up to 5; otherwise, it is a leak. Rajan should nudge users ordering 4 pizzas to add 1 more to unlock savings.

Q5. COGS +12% inflation — how many extra daily orders to hold EBITDA?

Ingredient costs increase by Rs.36/order, lowering the CM to Rs.475. To maintain the baseline monthly EBITDA, the outlet must secure ~3 extra orders/day (50 vs 47) or increase menu prices by Rs.36.

Q6. Three BI metrics from the database that improve profitability?

(1) Peak-hour heatmaps (FR-22) for staff scheduling. (2) Topping attach-rates (FR-17) for upselling higher margin items. (3) Repeat ordering rates by phone number to track aggregator-to-owned customer conversions.

Bottom Line Summary

SliceMatic is a fundamentally healthy single-outlet QSR with ~60% contribution margins and a ~13/day break-even it clears comfortably at mature volumes. The reference model is directionally right but optimistic by ~26% on margin. The business's fate rests on two levers the digital ordering system is purpose-built to move: order volume and owned-channel mix. Build the system to protect both, and the economics take care of themselves.
